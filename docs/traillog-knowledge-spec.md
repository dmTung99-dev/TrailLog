# TrailLog — Spec Kiến Thức Dự Án

**Mục đích tài liệu này:** cùng tinh thần với bản LexiCore (`lexi-core/docs/lexicore-knowledge-spec.md`) — bạn là người đưa ý tưởng/định hướng, AI viết phần lớn code, nhưng khi bị hỏi "bạn đã làm gì" thì câu trả lời phải là **hiểu vì sao code viết vậy và tự sửa/mở rộng được**, không phải "AI viết hết". Hai phần:

- **Phần 1 — Kiến thức nền tảng:** khái niệm chung, trả lời được kể cả không mở code.
- **Phần 2 — Áp dụng trong TrailLog:** đúng file, đúng dòng, đúng luồng thật trong dự án — để chỉ thẳng vào code khi bị hỏi "cho ví dụ cụ thể".

TrailLog được chọn **có chủ đích** để khác LexiCore: khác domain (theo dõi hoạt động ngoài trời thay vì học ngôn ngữ), khác nền tảng mobile (**React Native** thay vì Flutter), khác kiểu backend (**NestJS + PostgreSQL tự viết** thay vì Firebase serverless), khác mô hình dữ liệu (**offline-first thật với SQLite + sync engine tự viết** thay vì client ghi thẳng Firestore). Vì vậy tài liệu này ưu tiên các mảng mà **LexiCore không có**, và ở mỗi mục có bảng so sánh với cách làm tương ứng ở Flutter/LexiCore — đó chính là câu hỏi phỏng vấn dễ gặp nhất với một người "4 năm Flutter chuyển sang học React Native".

Tài liệu chọn **13 mảng kiến thức**, tất cả đã đối chiếu trực tiếp với code hiện tại (không chỉ dựa vào design spec/plan trong `docs/superpowers/`).

**Cấu trúc:** Phần 1 và Phần 2 **đánh số tương ứng 1–1** (mục 1.5 ↔ 2.5...). Mỗi mục ở Phần 1 theo cùng một khuôn — *Vấn đề nó giải quyết → Khái niệm cốt lõi → Cách hoạt động → Khi nào dùng/không dùng → Bẫy thường gặp → Câu hỏi phỏng vấn hay gặp* — rồi sang Phần 2 xem nó nằm ở đâu trong code thật (kèm chỗ khác biệt với LexiCore và các thoả hiệp/điểm yếu có thật).

> ⚠️ **Phát hiện quan trọng khi soạn tài liệu này — đọc trước khi nói "app chạy được trên máy thật":**

## 1.1 Quản lý state trong React Native: hook, Zustand, và so với Riverpod

### Vấn đề nó giải quyết

React dựng UI bằng **cây component**; mỗi lần state đổi, component **chạy lại hàm render** và React so sánh kết quả (reconciliation) để cập nhật phần thay đổi. State cục bộ (`useState`) bị nhốt trong một component. Khi nhiều màn hình cần chung một mẩu dữ liệu ("đang ghi hoạt động hay không", "đã đăng nhập chưa"), các cách thô đều đau:

- **Nâng state lên cha + truyền props** qua nhiều tầng (**prop drilling**).
- **React Context** — chia sẻ được, nhưng **mọi component dùng context rebuild khi bất kỳ phần nào của value đổi**, và cần bọc Provider.
- **Redux (cổ điển)** — mạnh, có devtools, nhưng nhiều boilerplate (action type, reducer, dispatch). Redux Toolkit giảm bớt nhưng vẫn nặng cho app nhỏ.

**Zustand** là thư viện store tối giản: một hàm `create()` trả về **một hook**; store sống **ngoài** cây component (không cần Provider), component chỉ rebuild khi phần state nó chọn thay đổi.

### Khái niệm cốt lõi

| Thuật ngữ | Nghĩa |
|---|---|
| **Hook** | Hàm bắt đầu bằng `use...`, chỉ gọi được ở top-level của component/hook khác (không trong `if`/vòng lặp) — vì React nhận diện hook theo **thứ tự gọi**. |
| **`useState`** | State cục bộ của một component. Đổi state → component render lại. |
| **`useEffect(fn, deps)`** | Chạy side-effect **sau** render; chạy lại khi một phần tử trong `deps` đổi; hàm trả về từ `fn` là **cleanup**. |
| **`useCallback(fn, deps)`** | Giữ **cùng một tham chiếu hàm** giữa các lần render (quan trọng khi hàm là dependency của effect khác). |
| **`useRef`** | Hộp giữ giá trị **không gây render lại** khi đổi (thường giữ tham chiếu tới component native, ví dụ camera). |
| **Zustand `create((set, get) => ({...}))`** | Khai báo store: state + action trong **một object**. `set(partial)` gộp nông (shallow merge) vào state; `get()` đọc state hiện tại bên trong action. |
| **Selector** | `useStore((s) => s.stepCount)` — component chỉ rebuild khi **giá trị được chọn** đổi. Gọi `useStore()` không có selector = đăng ký **toàn bộ** state. |
| **`useStore.getState()`** | Đọc store **ngoài** React (trong test, trong service) — không đăng ký theo dõi. |
| **Closure** | Hàm "nhớ" biến ở phạm vi nơi nó được tạo. Biến khai báo trong hàm khởi tạo store là **state riêng tư** không lộ ra UI. |

### So sánh với Riverpod (thứ bạn đã dùng ở LexiCore)

| | Riverpod (LexiCore) | Zustand (TrailLog) |
|---|---|---|
| Đơn vị | Nhiều **provider** nhỏ, có đồ thị phụ thuộc | Một **store** = một object lớn (state + action) |
| Phụ thuộc giữa các state | `ref.watch(other)` → tự tính lại | **Không có** cơ chế tự động; tự gọi store khác hoặc truyền tham số |
| Bất đồng bộ | `AsyncValue` (loading/data/error) có sẵn | Không có; tự thêm `status`/`error` vào state |
| Vòng đời | autoDispose / keepAlive | Store sống suốt app (module-level singleton) |
| Test | `ProviderContainer(overrides: [...])` | Đọc/ghi `getState()`/`setState()`; thay phụ thuộc bằng `jest.mock` hoặc "cửa sau" cho test |
| Boilerplate | Trung bình (code-gen) | Rất ít |
| Rủi ro | Dùng sai `watch`/`read` | Store thành "god object"; quên selector → rebuild thừa |

Câu chốt: **Riverpod là "đồ thị phụ thuộc có kiểu"; Zustand là "biến toàn cục có subscribe".** Zustand hợp khi state ít và ít phụ thuộc chéo.

### Cách hoạt động

`create()` tạo store + trả hook `useX`. Component gọi `useX(selector)` → Zustand đăng ký listener; khi `set()` được gọi, Zustand chạy selector với state mới, so sánh bằng `Object.is` với kết quả cũ, **khác thì mới** yêu cầu component render lại.

### Khi nào dùng / không dùng

- **Hợp:** app nhỏ–vừa, vài store độc lập, muốn ít boilerplate.
- **Không hợp:** nhiều state phụ thuộc chéo phức tạp, cần time-travel debugging, nhóm lớn cần quy ước chặt (→ Redux Toolkit), hoặc cần cache dữ liệu server có invalidation (→ TanStack Query).

### Bẫy thường gặp

1. **Không dùng selector** (`const {a, b} = useStore()`) → component rebuild với **mọi** thay đổi của store (ví dụ mỗi điểm GPS mới).
2. **Mutate state tại chỗ** (`state.list.push(x)`) → tham chiếu không đổi, UI không cập nhật. Luôn tạo object/mảng mới.
3. **State riêng tư trong closure** (không nằm trong `set`) → UI không thấy, devtools không thấy, và **tồn tại xuyên suốt các test** nếu không reset.
4. **Race condition trong action async**: hai lần gọi chồng nhau đều đọc state cũ trước khi `await` xong.
5. **Store module-level + test** → state rò rỉ giữa các test nếu không reset.

### Câu hỏi phỏng vấn hay gặp

- **Vì sao chọn Zustand thay Redux Toolkit?** — Ít boilerplate, không cần Provider, đủ cho 2 store nhỏ; đổi lại mất devtools/middleware mạnh và quy ước chặt của Redux.
- **Zustand khác Context ở đâu?** — Context rebuild mọi consumer khi value đổi; Zustand rebuild theo selector, và không cần bọc Provider.
- **`useEffect` với mảng deps rỗng chạy khi nào?** — Một lần sau lần render đầu (và cleanup khi unmount). Ở React 18 StrictMode dev, nó cố tình chạy **hai lần** để lộ lỗi thiếu cleanup.
- **So sánh với Flutter:** `setState` ↔ `useState`; `StatefulWidget.initState/dispose` ↔ `useEffect` + cleanup; Riverpod provider ↔ Zustand store.

## 1.2 Kiến trúc: tách service theo trách nhiệm + Ports & Adapters (không phải Clean Architecture đầy đủ)

### Vấn đề nó giải quyết

App có nhiều phần "chạm vào thế giới thật": GPS, cảm biến, camera, quyền hệ điều hành, SQLite, HTTP. Nếu component gọi thẳng những API này thì: (a) test phải giả lập cả điện thoại; (b) đổi thư viện (ví dụ SQLite → WatermelonDB) phải sửa khắp nơi; (c) logic khó (sync, đếm bước) bị trộn với UI.

### Khái niệm cốt lõi

- **Ports & Adapters (Hexagonal Architecture):** phần lõi khai báo **port** (interface — "tôi cần thứ gì đó chạy được SQL"), còn **adapter** là bản cài đặt cụ thể (SQLite trên máy thật, better-sqlite3 in-memory trong test). Lõi chỉ biết port.
- **Dependency Inversion:** module cấp cao (sync engine) phụ thuộc **abstraction** (`ActivitiesRepository`, `ApiClient`), không phụ thuộc chi tiết (`react-native-sqlite-storage`, `fetch`).
- **Factory function thay class + DI container:** trong TypeScript/JS rất phổ biến viết `createX(deps)` trả về object — phụ thuộc truyền qua tham số, không cần framework DI. (Backend NestJS thì ngược lại, dùng DI container — xem 1.10.)
- **Tách theo trách nhiệm (service-oriented):** mỗi service một việc — `LocationTrackingService` chỉ phát điểm GPS, không biết lưu ở đâu; `PedometerService` chỉ đếm bước; store mới là nơi **ghép** chúng lại.
- **Layer-first vs feature-first:** thư mục chia theo **loại kỹ thuật** (`api/`, `db/`, `sync/`, `screens/`...) là layer-first — hợp khi app nhỏ. LexiCore dùng feature-first + 3 tầng (`data/domain/presentation`) vì có ~15 tính năng.

### Khi nào dùng / không dùng

- **Hợp:** mọi chỗ chạm I/O hoặc native mà bạn muốn test không cần thiết bị.
- **Thừa:** bọc interface quanh thứ chỉ có một cách hiện thực và không cần test riêng — thêm tầng mà không thêm giá trị.

### Bẫy thường gặp

1. **Interface "rò rỉ"** — port mang kiểu dữ liệu của thư viện cụ thể (ví dụ trả về `ResultSet` của SQLite) → mất khả năng thay adapter.
2. **Component tự tạo phụ thuộc** (`createSqliteStorageAdapter()` ngay trong màn hình) → không tiêm được bản giả, phải `jest.mock` cả module.
3. **"Cửa sau cho test" lọt vào API thật** (method `__setXForTest`) — tiện nhưng làm bẩn interface production.

### Câu hỏi phỏng vấn hay gặp

- **Sao không dùng Clean Architecture đầy đủ như LexiCore?** — App có ít tính năng, logic nghiệp vụ tập trung ở sync và tracking; thêm tầng `domain/use_cases` cho mỗi thao tác CRUD sẽ là use case "mỏng". Giữ lại phần có giá trị nhất: interface ở ranh giới I/O.
- **Ports & Adapters giúp test thế nào?** — thay adapter thật bằng adapter giả **cùng hợp đồng**, test chạy trên Node không cần điện thoại.

## 1.3 Điều hướng: React Navigation (native stack) + "auth gate"

### Vấn đề nó giải quyết

React Native không có hệ thống điều hướng sẵn. **React Navigation** là thư viện phổ biến nhất; `native-stack` dùng **thành phần điều hướng native thật** (`UINavigationController` trên iOS, Fragment trên Android) nên chuyển màn mượt và đúng cảm giác nền tảng.

### Khái niệm cốt lõi

- **`NavigationContainer`**: gốc giữ state điều hướng. **`createNativeStackNavigator<ParamList>()`**: tạo stack có kiểu cho tham số từng màn.
- **`ParamList` (TypeScript)**: `{ ActivitySummary: { activityId: string } }` — khai báo màn nào nhận tham số gì; `navigation.navigate('ActivitySummary', { activityId })` được kiểm tra kiểu **nếu** bạn gõ đúng kiểu cho `navigation` (dùng `useNavigation<any>()` là **tắt** kiểm tra này).
- **`navigate` vs `push` vs `replace` vs `reset`**: `navigate` đi tới màn (nếu đã có trong stack thì quay về đó), `push` luôn chồng thêm, `replace` thay màn hiện tại, `reset` thay toàn bộ stack.
- **Màn hình không bị unmount khi bị che**: trong stack, màn phía dưới vẫn **mounted** khi bạn push màn mới lên. Vì vậy `useEffect([])` **không** chạy lại khi quay về. Muốn chạy lại mỗi khi màn được hiển thị → **`useFocusEffect`**.
- **Auth flow — hai cách:**
  1. **Điều kiện hoá cây màn hình** (cách React Navigation khuyến nghị): `{signedIn ? <Screen name="Home"/> : <Screen name="Login"/>}` — khi trạng thái đổi, cây đổi, người dùng **tự động** được chuyển; màn không được phép **không tồn tại** trong cây.
  2. **`initialRouteName` theo trạng thái** — chỉ quyết định màn **đầu tiên** lúc mount; sau đó đổi trạng thái **không** tự chuyển màn.

### So sánh với GoRouter (LexiCore)

| | GoRouter (LexiCore) | React Navigation (TrailLog) |
|---|---|---|
| Kiểu khai báo | Bảng route theo **URL/path** | Danh sách **màn có tên** trong navigator |
| Chặn truy cập | `redirect` chạy trước mỗi lần điều hướng + `refreshListenable` | Điều kiện hoá cây màn (hoặc `initialRouteName`, yếu hơn) |
| Trạng thái "chưa biết đã đăng nhập chưa" | Cờ `hasResolved` + màn `/splash` | Trạng thái `'checking'` → render `null`/splash |
| Deep link / web URL | Tự nhiên | Phải cấu hình `linking` riêng |
| Giữ state tab | `StatefulShellRoute` | Tab navigator giữ sẵn; stack giữ màn phía dưới mounted |

### Bẫy thường gặp

1. **Chỉ dùng `initialRouteName`** để gác cổng → đăng nhập xong không tự vào Home, đăng xuất không tự ra Login; và màn cần đăng nhập vẫn **tồn tại trong cây**, có thể điều hướng tới.
2. **Dữ liệu cũ khi quay lại màn**: dùng `useEffect([])` thay vì `useFocusEffect`.
3. **`useFocusEffect` không bọc `useCallback`** → effect chạy lại mỗi lần render (vòng lặp tải dữ liệu).
4. **`useNavigation<any>()`** → mất kiểm tra kiểu tên màn/tham số.

### Câu hỏi phỏng vấn hay gặp

- **Vì sao dùng `native-stack` thay `stack` (JS)?** — dùng primitive native, hiệu năng và cử chỉ vuốt-về đúng nền tảng; đổi lại ít tuỳ biến animation hơn.
- **Làm sao refresh dữ liệu khi quay lại màn?** — `useFocusEffect(useCallback(...))`.
- **Auth flow chuẩn trong React Navigation?** — điều kiện hoá cây màn theo trạng thái đăng nhập.

## 1.4 Offline-first với cơ sở dữ liệu cục bộ (SQLite)

### Vấn đề nó giải quyết

Người đi bộ đường dài thường ở nơi **không có sóng**. Nếu mỗi điểm GPS phải gửi lên server mới được lưu, app vô dụng đúng lúc cần nhất. **Offline-first**: mọi thao tác ghi vào **cơ sở dữ liệu trên máy trước**, không bao giờ chờ mạng; việc đẩy lên server là việc **riêng, làm sau**.

### Khái niệm cốt lõi

- **Local database là nguồn sự thật (source of truth) trên thiết bị** — UI đọc từ DB cục bộ, không đọc từ server.
- **SQLite:** CSDL quan hệ nhúng trong một file, có SQL đầy đủ, transaction, index. Trên RN truy cập qua native module (`react-native-sqlite-storage`, `op-sqlite`, `expo-sqlite`) hoặc qua ORM có đồng bộ sẵn (**WatermelonDB**).
- **Trạng thái đồng bộ theo từng bản ghi** (`sync_status`: `pending` / `synced` / `conflict`) + **id phía server** (`server_id`) tách khỏi **id cục bộ** — bản ghi được tạo offline chưa có id server.
- **UUID tạo ở client:** tạo id không cần hỏi server, không trùng giữa các máy. Trên RN cần polyfill `crypto.getRandomValues` (`react-native-get-random-values`) vì Hermes/JSC không có sẵn.
- **Migration schema:** app đã phát hành thì DB trên máy người dùng có schema cũ — phải có cách **nâng cấp** (theo số phiên bản `PRAGMA user_version`, hoặc thêm cột kiểu idempotent).
- **Transaction:** nhiều câu lệnh "tất cả hoặc không có gì". Không có transaction → lỗi giữa chừng để lại dữ liệu nửa vời.

### So sánh với LexiCore

| | LexiCore (hiện tại) | TrailLog |
|---|---|---|
| Kho chính trên máy | Không có (Hive chỉ còn migration 1 lần); dựa vào cache mặc định của Firestore SDK | **SQLite** là nguồn sự thật trên máy |
| Đồng bộ | SDK Firestore tự lo | **Tự viết** sync engine (1.5) |
| Làm việc offline | Chưa kiểm chứng | Mục tiêu thiết kế cốt lõi |
| Xung đột | Firestore last-write-wins mặc định | Tự phát hiện, cho người dùng chọn (1.6) |

### Khi nào dùng / không dùng

- **Hợp:** dữ liệu do chính người dùng tạo, phải ghi được khi mất mạng, khối lượng ghi cao (GPS mỗi 5 giây).
- **Không hợp / đắt:** dữ liệu cộng tác thời gian thực nhiều người cùng sửa (cần CRDT/OT), hoặc dữ liệu chủ yếu đọc từ server (dùng cache HTTP là đủ).

### Bẫy thường gặp

1. **Không có transaction** → nhiều `UPDATE` rời rạc, lỗi giữa chừng để lại trạng thái nửa vời.
2. **N+1 query:** lấy danh sách rồi mỗi dòng lại query con → chậm theo số bản ghi.
3. **Mở nhiều kết nối** tới cùng file → tốn tài nguyên, có thể gặp lỗi khoá (`database is locked`).
4. **Ghi "bắn rồi quên"** (không `await`, không bắt lỗi) → lỗi ghi biến mất im lặng, mất dữ liệu mà không ai biết.
5. **Không có index/khoá ngoại** → truy vấn con chậm, bản ghi mồ côi khi xoá cha.
6. **Lưu thời gian bằng giờ máy** → giờ máy có thể sai (xem 1.6).

### Câu hỏi phỏng vấn hay gặp

- **Offline-first khác "có cache" ở đâu?** — Cache là bản sao phụ của server; offline-first coi local là nguồn chính và server là nơi hội tụ về sau.
- **Vì sao id tạo ở client?** — để tạo bản ghi khi không có mạng; UUID v4 xác suất trùng không đáng kể.
- **Migration schema ở mobile khó hơn backend ở đâu?** — không kiểm soát được khi nào người dùng cập nhật app; phải nâng cấp được từ **mọi** phiên bản cũ.

## 1.5 Sync engine: hàng đợi outbox, idempotency, khả năng tiếp tục (resumability)

### Vấn đề nó giải quyết

Dữ liệu tạo offline cần được đẩy lên server **đúng một lần, không mất, không trùng**, dù mạng có thể đứt **giữa chừng** một chuỗi nhiều request (tạo hoạt động → tạo từng checkpoint → tải từng ảnh).

### Khái niệm cốt lõi

- **Outbox pattern:** mỗi bản ghi cục bộ có cờ "chưa đồng bộ"; sync engine định kỳ/khi được gọi quét những bản ghi đó và đẩy lên. "Hàng đợi" chính là **truy vấn** `WHERE sync_status = 'pending'`.
- **Idempotency (tính luỹ đẳng):** làm một thao tác nhiều lần cho **cùng kết quả** như làm một lần. Có hai phía:
  - **Phía client:** ghi nhớ bước nào đã xong (`server_id` đã có → không tạo lại; `photo_uploaded = 1` → không tải lại).
  - **Phía server:** **idempotency key** — client gửi kèm một id duy nhất cho mỗi thao tác tạo; server thấy key đã xử lý thì trả lại kết quả cũ thay vì tạo bản mới. Cần thiết vì **response có thể mất sau khi server đã ghi xong** — client không biết request thành công hay không.
- **Resumability:** sync bị ngắt ở bước k thì lần sau tiếp tục từ bước k, không làm lại từ đầu, không bỏ sót.
- **Bất biến "trạng thái kết thúc ghi sau cùng":** bất kỳ thao tác nào **đưa bản ghi ra khỏi hàng đợi** (đánh dấu `synced` hoặc `conflict`) chỉ được ghi **sau khi** mọi bước con đã thành công. Ghi sớm + lỗi ở bước sau = bản ghi rời hàng đợi với dữ liệu con chưa đồng bộ, **mắc kẹt vĩnh viễn**.
- **At-least-once vs exactly-once:** mạng chỉ cho bạn "ít nhất một lần" (retry); "đúng một lần" phải tự dựng bằng idempotency.
- **Retry với exponential backoff + jitter:** thử lại với khoảng chờ tăng dần (1s, 2s, 4s...) + ngẫu nhiên nhỏ để hàng nghìn máy không cùng dội vào server một lúc.
- **Push vs pull:** push = đẩy thay đổi cục bộ lên; pull = kéo thay đổi từ server (ví dụ dữ liệu tạo trên thiết bị khác) về.
- **Kích hoạt sync:** thủ công (nút bấm), khi có mạng trở lại (`NetInfo`), khi app vào foreground, hoặc theo lịch nền (`WorkManager`/`BGTaskScheduler`).

### Cách hoạt động (một vòng push điển hình)

`listPending()` → với mỗi bản ghi: chưa có `server_id` → `POST` tạo, **ghi `server_id` ngay** (nhưng vẫn giữ `pending`) → với mỗi bản ghi con chưa có `server_id` → tạo, ghi `server_id` con → với mỗi ảnh chưa tải → tải, ghi cờ → **cuối cùng** mới ghi `synced`. Bất kỳ bước nào ném lỗi → dừng bản ghi này, giữ `pending`, lần sau tiếp tục.

### Khi nào dùng / đánh đổi

- **Tự viết sync** cho bạn toàn quyền (thứ tự, xung đột, định dạng), nhưng là **phần dễ sai nhất** của cả app. Giải pháp có sẵn (WatermelonDB sync, PowerSync, Realm/Atlas Device Sync, Firestore) đổi quyền kiểm soát lấy độ tin cậy.

### Bẫy thường gặp

1. **Đánh dấu "đã đồng bộ" trước khi bản ghi con xong** → mất dữ liệu im lặng (đây là bug có thật đã sửa 3 lần trong TrailLog — xem §2.5).
2. **Không có idempotency phía server** → retry sau khi mất response tạo **bản trùng** trên server.
3. **Chạy hai vòng sync song song** → cùng một bản ghi bị đẩy hai lần.
4. **Nuốt mọi lỗi thành "failed"** → không phân biệt lỗi tạm (mất mạng, 5xx — nên thử lại) với lỗi vĩnh viễn (400, 401 — thử lại vô ích, cần xử lý khác).
5. **Chỉ push mà không pull** → "đồng bộ đa thiết bị" chỉ là một chiều.

### Câu hỏi phỏng vấn hay gặp

- **Làm sao để retry không tạo bản trùng?** — idempotency: client nhớ bước đã xong; server dùng idempotency key hoặc id do client cấp.
- **Nếu request tạo thành công nhưng response bị mất?** — client sẽ tạo lại → trùng, **trừ khi** server có idempotency. Đây là câu hỏi phân loại người hiểu sync thật sự.
- **Exponential backoff để làm gì, jitter để làm gì?** — giảm tải khi server gặp sự cố; tránh "thundering herd".

## 1.6 Phát hiện xung đột: optimistic concurrency, last-write-wins, và vấn đề đồng hồ

### Vấn đề nó giải quyết

Cùng một hoạt động được sửa tiêu đề trên **điện thoại A** và **điện thoại B** khi cả hai offline. Khi cả hai đồng bộ, server phải quyết định: ghi đè, gộp, hay hỏi người dùng?

### Khái niệm cốt lõi

- **Pessimistic locking:** khoá bản ghi trước khi sửa — không khả thi khi thiết bị offline.
- **Optimistic concurrency control (OCC):** không khoá; khi ghi, client gửi kèm **"phiên bản tôi đã thấy"**; server chỉ chấp nhận nếu phiên bản hiện tại **vẫn là** phiên bản đó, ngược lại báo **xung đột**. Tương đương HTTP `If-Match` + `ETag` → `412 Precondition Failed`.
- **Mã phiên bản:** số nguyên tăng dần (`version`) — đáng tin nhất; hoặc `updatedAt` của **server** — đủ dùng nếu so đúng cách.
- **"Đã thấy" (base version) khác "lần sửa cục bộ":** để phát hiện "cả hai phía cùng đổi kể từ lần đồng bộ cuối", client phải nhớ **phiên bản server lúc đồng bộ cuối** (base). So `server.version > base` = server đã đổi. Nếu client gửi **thời điểm nó sửa cục bộ** thay vì base, phép so thành "ai sửa muộn hơn theo đồng hồ" → **last-write-wins theo đồng hồ treo tường**.
- **Last-write-wins (LWW):** bản ghi có thời điểm muộn hơn thắng. Đơn giản nhưng **âm thầm mất** thay đổi của bên kia.
- **Clock skew (lệch đồng hồ):** đồng hồ điện thoại có thể lệch vài giây tới vài giờ (người dùng chỉnh tay, múi giờ, mất NTP). So thời điểm **giữa hai máy khác nhau** là không đáng tin. Hybrid Logical Clock / vector clock là cách giải trong hệ phân tán.
- **Kiểm-rồi-ghi (check-then-act) không nguyên tử:** đọc phiên bản, so sánh, rồi `UPDATE` bằng hai câu lệnh riêng → hai request đồng thời đều qua được bước kiểm. Cách đúng: `UPDATE ... WHERE id = ? AND version = ?` rồi xem số dòng bị ảnh hưởng (atomic compare-and-swap).
- **Chiến lược giải quyết:** LWW tự động / gộp theo trường (field-level merge) / **cho người dùng chọn** / CRDT (tự gộp, cho dữ liệu cộng tác).

### Khi nào dùng / đánh đổi

- **Hỏi người dùng** chỉ đáng khi xung đột **hiếm** và dữ liệu **có giá trị** (tiêu đề/ghi chú hoạt động) — hỏi quá nhiều thì người dùng bấm bừa.
- Dữ liệu chỉ-thêm (append-only) như điểm GPS **không thể** xung đột — không cần OCC.

### Bẫy thường gặp

1. **So thời điểm sửa cục bộ với thời điểm server** → phụ thuộc đồng hồ máy, thành LWW ngầm.
2. **Check-then-act không nguyên tử** trên server.
3. **Giải quyết xung đột xong nhưng không cập nhật base** → lần sau lại báo xung đột (hoặc không bao giờ báo nữa).
4. **"Lấy bản server" nhưng chỉ lấy một phần trường**.

### Câu hỏi phỏng vấn hay gặp

- **Optimistic vs pessimistic locking?** — OCC phát hiện xung đột lúc ghi; pessimistic ngăn xung đột bằng khoá. Offline chỉ dùng được OCC.
- **Vì sao `updatedAt` không lý tưởng làm phiên bản?** — độ phân giải thời gian, phụ thuộc đồng hồ; số `version` nguyên tăng dần rõ ràng hơn.
- **ETag/If-Match là gì?** — chuẩn HTTP cho OCC.

## 1.7 Theo dõi vị trí nền: Android foreground service, iOS background mode, native module, state machine

### Vấn đề nó giải quyết

Người dùng tắt màn hình, bỏ điện thoại vào túi. Hệ điều hành **muốn giết** app nền để tiết kiệm pin. Muốn tiếp tục nhận GPS thì phải "xin phép" hệ điều hành theo cách **khác nhau hoàn toàn** giữa Android và iOS. Đây là tính năng mà React Native và Flutter **đều phải xuống tầng native** — nên là bài học native-module thật sự.

### Khái niệm cốt lõi

- **Native module:** code Kotlin/Java/Swift/ObjC lộ ra cho JavaScript. Kiến trúc cũ dùng **Bridge** (JSON bất đồng bộ qua hàng đợi); kiến trúc mới (RN ≥ 0.68, mặc định từ 0.76) dùng **JSI + TurboModules** (gọi trực tiếp C++, có thể đồng bộ) và **Fabric** (renderer mới). RN 0.75 vẫn mặc định kiến trúc cũ. Flutter tương đương: **platform channel** / **Pigeon** / FFI.
- **Android — Foreground Service:** dịch vụ chạy nền **kèm thông báo cố định** ("TrailLog đang ghi lộ trình") — hệ điều hành ít giết hơn nhiều. Android 14+ bắt buộc khai báo **`foregroundServiceType="location"`** và quyền `FOREGROUND_SERVICE_LOCATION`. Android 10+ còn có quyền **`ACCESS_BACKGROUND_LOCATION`** riêng khi cần vị trí lúc app **không** có foreground service.
- **iOS — Background Modes:** khai báo `UIBackgroundModes: location` trong `Info.plist`, xin quyền "When In Use" hoặc "Always"; iOS tự **tiết chế** (throttle) và có thể dừng cập nhật nếu app không thực sự cần. Không có khái niệm "foreground service".
- **JS thread khi app nền:** trên Android, JS chỉ tiếp tục chạy nếu có gì đó giữ process sống (foreground service). Thư viện như `react-native-background-actions` chạy một **headless task** giữ JS sống — **task kết thúc khi Promise của nó resolve**.
- **`watchPosition` + `distanceFilter` + `interval`:** đăng ký nhận vị trí liên tục; `distanceFilter` = chỉ báo khi di chuyển ≥ N mét (tiết kiệm pin và giảm nhiễu), `interval` (Android) = chu kỳ mong muốn.
- **Finite State Machine (FSM):** mô hình hoá vòng đời bằng **tập trạng thái hữu hạn** + **bảng chuyển trạng thái hợp lệ**. Chuyển không hợp lệ (Pause khi đang Idle) bị **từ chối rõ ràng** thay vì để hệ thống vào trạng thái lạ. Là hàm thuần → test dễ.

### Cách hoạt động (Android)

Start → khởi động foreground service (thông báo xuất hiện, JS được giữ sống) → `watchPosition` → mỗi điểm mới gọi callback → ghi SQLite. Pause → **chỉ** ngừng `watchPosition`, **giữ** service. Stop → ngừng watch, **resolve** Promise của task → thư viện gỡ service.

### Khi nào dùng / đánh đổi

- **Hợp:** ghi lộ trình liên tục trong phiên do người dùng chủ động bắt đầu.
- **Đánh đổi:** tốn pin; chịu sự khác biệt giữa các hãng Android (Xiaomi/Huawei/Samsung có "tối ưu pin" riêng giết cả foreground service — xem dontkillmyapp.com); iOS có thể tiết chế bất kể bạn làm gì.

### Bẫy thường gặp

1. **Promise của task nền resolve sớm** → thư viện tưởng task xong, gỡ service → mất GPS khi tắt màn hình.
2. **Bật/tắt service mỗi lần Pause/Resume** → race giữa `stop()` cũ và `start()` mới, vì thư viện là **singleton native** không cô lập theo instance.
3. **Start–Stop–Start nhanh** trước khi teardown xong → hai task chồng nhau.
4. **Thiếu `foregroundServiceType`** trên Android 14 → crash khi start service.
5. **Chỉ test bằng mock** → mọi hành vi thật của OS (throttle, kill, quyền) chưa được kiểm chứng.

### Câu hỏi phỏng vấn hay gặp

- **Khác biệt Android/iOS khi chạy nền?** — Android: foreground service + thông báo; iOS: background mode + OS tự tiết chế.
- **Bridge vs JSI?** — Bridge: serialize JSON, bất đồng bộ, có độ trễ; JSI: gọi trực tiếp qua C++, có thể đồng bộ, không serialize.
- **So với Flutter?** — Flutter cũng phải dùng plugin native (`geolocator`, `flutter_background_service`); khác ở chỗ RN chạy JS trong engine riêng (Hermes) còn Flutter biên dịch AOT Dart — nhưng vấn đề nền của OS là **như nhau**.
- **Vì sao dùng state machine?** — biến "chuỗi if lồng nhau về trạng thái" thành bảng dữ liệu có thể test đầy đủ; chặn chuyển trạng thái sai ngay lập tức.

## 1.8 Cảm biến & đếm bước: xử lý tín hiệu gia tốc, stream (RxJS), stateful accumulator

### Vấn đề nó giải quyết

Đếm bước chân từ **gia tốc kế** (accelerometer) thô: cảm biến trả 50 mẫu/giây `(x, y, z)`, mỗi bước chân tạo một "đỉnh" gia tốc. Cần biến chuỗi số nhiễu thành số bước tin cậy.

### Khái niệm cốt lõi

- **Độ lớn vector (magnitude):** `√(x² + y² + z²)` — không phụ thuộc hướng cầm máy. Khi đứng yên ≈ **9.8 m/s²** (trọng trường).
- **Phát hiện đỉnh (peak detection) bằng ngưỡng:** đếm khi `magnitude − 9.8` **vượt lên** trên ngưỡng (phát hiện **cạnh lên** — rising edge — chứ không đếm mọi mẫu ở trên ngưỡng).
- **Debounce / thời gian trơ (refractory period):** hai bước không thể cách nhau < ~250 ms → bỏ qua đỉnh quá gần.
- **Batch vs streaming:** hàm batch nhận cả mảng mẫu và trả số bước; xử lý **streaming** nhận từng mẫu một và phải **mang trạng thái** (đỉnh trước ở đâu, đang ở trên ngưỡng không) qua các lần gọi.
- **Bug "cửa sổ trượt":** nếu mỗi mẫu mới lại chạy hàm batch trên N mẫu gần nhất, kết quả là **số bước trong cửa sổ**, không phải tổng — số bị chặn trên và có thể **giảm**.
- **Observable (RxJS):** dòng giá trị theo thời gian; `subscribe()` trả `Subscription`, **phải** `unsubscribe()` để dừng cảm biến. Tương đương `Stream`/`StreamSubscription.cancel()` trong Dart.
- **Pedometer phần cứng:** iOS (`CMPedometer`) và Android (`TYPE_STEP_COUNTER`) có bộ đếm bước **chip riêng**, chính xác hơn và tiết kiệm pin hơn tự tính từ gia tốc — nhưng cần quyền (iOS Motion, Android 10+ `ACTIVITY_RECOGNITION`).

### Khi nào dùng / đánh đổi

- **Tự tính từ gia tốc:** kiểm soát thuật toán, dạy được xử lý tín hiệu; đổi lại kém chính xác (xe cộ, lắc tay) và **tốn pin** (lấy mẫu 50 Hz liên tục, và JS phải chạy suốt).
- **Dùng pedometer hệ thống:** chính xác, rẻ pin; phụ thuộc thiết bị.

### Bẫy thường gặp

1. **Đếm mọi mẫu trên ngưỡng** thay vì cạnh lên → một bước đếm nhiều lần.
2. **Mất trạng thái ở ranh giới cửa sổ/buffer** → bỏ sót hoặc đếm đôi.
3. **Quên unsubscribe** → cảm biến chạy mãi, hao pin, rò rỉ.
4. **Hằng số ngưỡng "ma thuật"** chưa hiệu chỉnh trên thiết bị thật.

### Câu hỏi phỏng vấn hay gặp

- **Vì sao dùng magnitude thay vì trục z?** — không phụ thuộc hướng cầm máy.
- **Vì sao cần debounce?** — một bước tạo nhiều dao động nhỏ quanh đỉnh.
- **Bug streaming nào hay gặp?** — tính lại trên cửa sổ trượt thay vì tích luỹ trạng thái.

## 1.9 Quyền hệ điều hành (runtime permissions) và suy giảm mềm (graceful degradation)

### Vấn đề nó giải quyết

Vị trí, camera, chuyển động là **quyền nguy hiểm** — phải hỏi người dùng lúc chạy. Kết quả có **nhiều hơn hai trạng thái** và khác nhau giữa nền tảng; mỗi màn hình tự xử lý thì mỗi nơi một kiểu.

### Khái niệm cốt lõi

- **Các trạng thái (theo `react-native-permissions`):** `granted`, `denied` (có thể hỏi lại), `blocked` (người dùng chọn "không hỏi lại" — chỉ còn cách mở Cài đặt), `limited` (iOS: ảnh giới hạn), `unavailable` (thiết bị không có).
- **Vị trí chính xác vs gần đúng:** Android 12+ cho người dùng chọn **"Approximate"** — cấp `COARSE` nhưng từ chối `FINE`. iOS 14+ có công tắc **Precise Location**. Với app ghi lộ trình, vị trí gần đúng (sai số hàng km) gần như vô dụng nhưng **không phải lỗi** — nên cảnh báo, không nên chặn.
- **Chuẩn hoá (normalization):** ánh xạ tổ hợp kết quả thô của từng nền tảng về **một enum của app** (`granted` / `approximate-only` / `denied` / `restricted`) — mọi màn hình chỉ xử lý enum này.
- **Graceful degradation:** thiếu quyền **phụ** (chuyển động) → vẫn chạy phần chính, chỉ tắt tính năng phụ (đếm bước); thiếu quyền **chính** (vị trí) → không bắt đầu.
- **Quyền phải xin trước khi chạm API native** — gọi API trước khi có quyền có thể ném lỗi hoặc âm thầm không làm gì.

### Bẫy thường gặp

1. **Coi `denied` và `blocked` như nhau** → hỏi lại mãi mà hộp thoại không bao giờ hiện (vì đã blocked). Phải hướng người dùng tới Cài đặt (`openSettings()`).
2. **Không xử lý "approximate-only"** → lộ trình vẽ ra lệch hàng km mà người dùng không hiểu vì sao.
3. **Từ chối âm thầm** — bấm nút không có phản hồi gì.
4. **Chỉ xin "When In Use" nhưng mong chạy nền** — trên iOS, chạy nền lâu cần "Always" (hoặc chấp nhận chỉ báo xanh "đang dùng vị trí").

### Câu hỏi phỏng vấn hay gặp

- **`denied` khác `blocked`?** — `denied` còn hỏi lại được; `blocked` phải mở Cài đặt.
- **Vì sao chuẩn hoá quyền về một enum?** — một nơi chứa logic khác biệt nền tảng; UI chỉ xử lý các trường hợp có ý nghĩa với sản phẩm.

## 1.10 Backend NestJS: module, DI container, decorator, guard, pipe, DTO

### Vấn đề nó giải quyết

Express thuần cho tự do tuyệt đối nhưng không có cấu trúc: mỗi dự án tự nghĩ cách tổ chức route, validate, xác thực, tiêm phụ thuộc. **NestJS** là framework "có ý kiến" (opinionated), lấy cảm hứng Angular: tổ chức theo **module**, có **DI container**, dùng **decorator** để khai báo — code backend TypeScript có cấu trúc nhất quán, test được.

### Khái niệm cốt lõi

| Khái niệm | Vai trò |
|---|---|
| **Module (`@Module`)** | Gom controller + provider của một miền; `imports` module khác, `exports` provider cho module khác dùng. `@Global()` = không cần import. |
| **Provider / DI** | Class `@Injectable()` được Nest **tự tạo và tiêm** qua constructor. Mặc định **singleton**. |
| **Custom provider token** | `{ provide: TOKEN, useClass: Impl }` — tiêm theo **token** (thường là `Symbol` hoặc chuỗi) để phụ thuộc vào **interface** (TypeScript interface biến mất lúc chạy nên không dùng làm token được) → `@Inject(TOKEN)`. |
| **Controller** | `@Controller('path')`, `@Get/@Post/@Patch`, `@Param`, `@Body`, `@Req`. Trả object → Nest tự serialize JSON. |
| **Guard** | Chạy **trước** handler, quyết định cho qua hay không (`canActivate`). Dùng cho xác thực/phân quyền. `@UseGuards(...)`. |
| **Pipe** | Biến đổi/kiểm tra input. **`ValidationPipe`** dùng `class-validator` trên DTO; `whitelist: true` **bỏ** trường không khai báo; `transform: true` chuyển payload thành instance DTO. |
| **DTO + class-validator** | Class mô tả hình dạng input với decorator (`@IsString`, `@IsDateString`, `@ValidateNested` + `@Type`). |
| **Exception filter** | `throw new NotFoundException()` → Nest tự trả 404 JSON. |
| **Interceptor** | Bọc quanh handler (ví dụ `FileInterceptor` của Multer xử lý upload multipart). |
| **Lifecycle hook** | `OnModuleInit`/`OnModuleDestroy` — mở/đóng kết nối DB. |

**Thứ tự trong một request:** Middleware → **Guard** → Interceptor (trước) → **Pipe** → **Handler** → Interceptor (sau) → Exception filter (nếu có lỗi).

### So sánh với Cloud Functions (LexiCore)

| | Cloud Functions `onCall` (LexiCore) | NestJS (TrailLog) |
|---|---|---|
| Kiểu | Hàm serverless, mỗi hàm một endpoint | Server chạy liên tục, nhiều route |
| Xác thực | SDK tự đính ID token, `request.auth` có sẵn | Tự dựng: JWT + Passport + Guard |
| Validate input | Tự viết type guard | `ValidationPipe` + DTO decorator |
| DB | Firestore (NoSQL) | PostgreSQL qua Prisma (SQL) |
| Hạ tầng | Không phải quản lý | Phải tự deploy (container/VM) + quản lý DB |

### Bẫy thường gặp

1. **Quên `whitelist`** → client gửi thêm trường (ví dụ `userId`) có thể lọt vào DB qua spread.
2. **DTO lồng nhau thiếu `@Type(() => X)`** → `@ValidateNested` không validate gì (object thường không phải instance).
3. **Guard đặt sai cấp** (quên trên controller mới) → endpoint mở.
4. **Logic nghiệp vụ trong controller** (gọi thẳng Prisma) → khó test, trùng lặp.
5. **Đọc `process.env` rải rác kèm giá trị mặc định** thay vì qua `ConfigService` có validate → thiếu biến môi trường mà không ai biết.

### Câu hỏi phỏng vấn hay gặp

- **Guard khác middleware?** — Guard biết **handler nào** sắp chạy (có `ExecutionContext`, đọc được metadata) — hợp cho phân quyền; middleware thì không.
- **Vì sao cần token `Symbol` cho provider?** — interface TypeScript bị xoá khi biên dịch, không dùng làm khoá DI được.
- **`whitelist` và `forbidNonWhitelisted` khác nhau?** — `whitelist` lặng lẽ bỏ trường lạ; `forbidNonWhitelisted` trả 400.

## 1.11 Xác thực: bcrypt + JWT + Passport, và lưu token trên mobile

### Vấn đề nó giải quyết

Tự viết đăng ký/đăng nhập email–mật khẩu (thay vì Firebase Auth như LexiCore) — phải tự lo: lưu mật khẩu an toàn, cấp token, kiểm tra token mỗi request, lưu token trên máy.

### Khái niệm cốt lõi

- **Băm mật khẩu bằng bcrypt:** hàm băm **chậm có chủ đích** với **cost factor** (10 = 2¹⁰ vòng) và **salt** ngẫu nhiên nhúng sẵn trong chuỗi băm → chống bảng tra sẵn (rainbow table) và brute-force. **Không bao giờ** dùng SHA-256 thuần cho mật khẩu. (Argon2id là lựa chọn hiện đại hơn.)
- **JWT (JSON Web Token):** `header.payload.signature`. Payload có claim `sub` (id người dùng), `exp` (hết hạn). Ký bằng **HS256 + secret** (đối xứng) hoặc RS256 (bất đối xứng). Server **không cần lưu phiên** — chỉ kiểm chữ ký + hạn (**stateless**).
- **Nhược điểm stateless:** **không thu hồi được** token trước khi hết hạn (đăng xuất chỉ xoá ở client; token bị đánh cắp vẫn dùng được tới `exp`).
- **Access token ngắn hạn + refresh token dài hạn:** access token sống 5–15 phút; refresh token lưu phía server (có thể thu hồi) dùng để xin access token mới — cân bằng giữa stateless và thu hồi được.
- **Passport + `passport-jwt`:** strategy lấy token từ header `Authorization: Bearer ...`, kiểm chữ ký/hạn, gọi `validate(payload)` — giá trị trả về gắn vào `req.user`.
- **Lưu token trên mobile:**
  - **AsyncStorage** — key-value **không mã hoá** (SharedPreferences/file). Đơn giản, nhưng ai đọc được bộ nhớ app (máy root/jailbreak, backup) đọc được token.
  - **Keychain (iOS) / Keystore + EncryptedSharedPreferences (Android)** qua `react-native-keychain` / `expo-secure-store` — mã hoá bằng khoá phần cứng. Tương đương `flutter_secure_storage`.
- **User enumeration:** thông báo lỗi hoặc **thời gian phản hồi** khác nhau giữa "email không tồn tại" và "sai mật khẩu" cho phép dò email nào đã đăng ký.

### Bẫy thường gặp

1. **Secret JWT có giá trị mặc định trong code** → quên đặt biến môi trường là ai cũng ký được token giả.
2. **Token sống lâu, không refresh, không thu hồi**.
3. **Lưu token ở storage không mã hoá**.
4. **Client không xử lý 401** → token hết hạn, app vẫn tưởng đã đăng nhập, mọi request thất bại.
5. **Khôi phục phiên chỉ kiểm "có token không"** mà không kiểm hạn.

### Câu hỏi phỏng vấn hay gặp

- **Vì sao bcrypt chứ không SHA-256?** — bcrypt chậm có chủ đích + salt; SHA-256 nhanh → brute-force GPU rẻ.
- **JWT stateless nghĩa là gì, đánh đổi gì?** — server không lưu phiên; đổi lại khó thu hồi.
- **Lưu token ở đâu trên mobile?** — Keychain/Keystore, không phải AsyncStorage.
- **So với Firebase Auth (LexiCore)?** — Firebase lo sẵn băm mật khẩu, refresh token, thu hồi; tự viết thì mọi thứ đó là trách nhiệm của bạn.

## 1.12 PostgreSQL + Prisma: schema, migration, quan hệ, kiểm tra sở hữu

### Vấn đề nó giải quyết

Cần CSDL quan hệ phía server với **kiểu an toàn** trong TypeScript và **lịch sử thay đổi schema** có kiểm soát.

### Khái niệm cốt lõi

- **Prisma schema (`schema.prisma`):** một file khai báo model; **Prisma Client** được sinh ra có kiểu đầy đủ (`prisma.activity.findFirst({ where, include })`).
- **Migration:** `prisma migrate dev` so schema với DB, sinh file SQL trong `prisma/migrations/` (được commit vào git); `prisma migrate deploy` áp dụng ở CI/production. Khác Firestore (LexiCore) — không có schema, không có migration.
- **Quan hệ + khoá ngoại:** `@relation(fields, references, onDelete: Cascade)` tạo **foreign key** trong DB — xoá cha thì xoá con, và DB **từ chối** con trỏ tới cha không tồn tại.
- **Nested write:** `create({ data: { routePoints: { create: [...] } } })` — tạo cha và con trong **một transaction**.
- **`@updatedAt`:** Prisma tự đặt thời điểm mỗi lần update qua Prisma Client.
- **Kiểm tra sở hữu (ownership check / chống IDOR):** mọi truy vấn theo id phải kèm `userId` của người gọi (`where: { id, userId }`). Thiếu nó = **IDOR** (Insecure Direct Object Reference) — đoán id là đọc được dữ liệu người khác.
- **404 thay vì 403** cho tài nguyên của người khác → không tiết lộ tài nguyên đó **có tồn tại**.
- **Prisma vs TypeORM:** Prisma — schema-first, client sinh sẵn, kiểu chặt; TypeORM — entity class + decorator, Active Record/Data Mapper, linh hoạt hơn nhưng kiểu lỏng hơn.

### Bẫy thường gặp

1. **Cột `userId` không có `@relation`** → không có khoá ngoại; xoá user để lại dữ liệu mồ côi, và DB chấp nhận `userId` rác.
2. **Thiếu index** trên cột hay lọc (`userId`, `activityId`) → PostgreSQL **không tự tạo index cho khoá ngoại**.
3. **Kiểm-rồi-ghi hai câu lệnh** → race (xem 1.6).
4. **Quên `userId` trong một truy vấn con** (ví dụ tìm checkpoint theo id mà không ràng buộc activity) → IDOR.

### Câu hỏi phỏng vấn hay gặp

- **IDOR là gì, chặn thế nào?** — truy cập tài nguyên qua id đoán được; luôn lọc theo chủ sở hữu ở tầng truy vấn.
- **Vì sao trả 404 thay vì 403?** — không lộ sự tồn tại.
- **Migration trong CI chạy lệnh nào?** — `prisma migrate deploy` (không sinh migration mới, chỉ áp dụng).

## 1.13 Testing & CI: test double, real-SQL fake, RNTL, e2e với DB thật, Detox

### Vấn đề nó giải quyết

Phần khó nhất của TrailLog (sync, tracking lifecycle) là nơi bug **âm thầm mất dữ liệu**. Không có test tốt thì mỗi lần sửa là một lần đánh cược — và phần lớn code do AI viết, nên test là **đặc tả mà bạn kiểm soát**.

### Khái niệm cốt lõi

- **Kim tự tháp test:** nhiều unit → ít integration/component → rất ít e2e.
- **Test double:** stub (trả kết quả định sẵn), mock (kiểm tra được gọi thế nào — `jest.fn()`), **fake** (bản cài đặt đơn giản nhưng chạy thật — ví dụ SQLite in-memory).
- **Real-SQL fake:** thay SQLite native (không chạy được trên Node) bằng **better-sqlite3 in-memory** (SQLite thật, chạy trên Node) qua **cùng interface** → test chạy **SQL thật**, bắt được lỗi cú pháp/logic SQL mà mock bỏ sót.
- **`jest.mock` / `moduleNameMapper`:** thay cả module native (GPS, camera, cảm biến) bằng file mock JS — bắt buộc vì Jest chạy trên Node, không có điện thoại.
- **React Native Testing Library (RNTL):** render component trong môi trường test, tương tác như người dùng (`fireEvent.press(getByText('Start'))`), chờ bằng `findBy*`/`waitFor`. Nguyên tắc: test **hành vi nhìn thấy được**, không test chi tiết cài đặt.
- **Backend e2e với PostgreSQL thật:** dựng app NestJS thật (`Test.createTestingModule`), gọi HTTP bằng `supertest`, chạy trên DB Postgres thật (container service ở CI) — bắt lỗi mà mock Prisma không thấy (ràng buộc unique, kiểu cột, migration).
- **Detox:** e2e **gray-box** cho RN — chạy app thật trên emulator, tự **đồng bộ** với trạng thái idle của app (đợi animation/network xong) nên ít flaky hơn Appium.
- **Flaky test** do thời gian/cache: lần chạy đầu biên dịch (transform) chậm → vượt timeout.
- **CI (GitHub Actions):** mỗi push/PR chạy lint + typecheck + test; e2e mobile tốn emulator nên chạy riêng/thủ công.

### Bẫy thường gặp

1. **Mock quá đà** → test xanh nhưng hành vi thật sai (đặc biệt với API native).
2. **Nhiều file e2e chạy song song trên cùng một DB** và cùng `deleteMany()` → xoá dữ liệu của nhau → flaky. Dùng `--runInBand` hoặc DB/schema riêng mỗi worker.
3. **State module-level rò rỉ giữa test** (store Zustand, biến singleton).
4. **Tên test nói một đằng, assert một nẻo**.
5. **CI chỉ trigger trên nhánh không dùng** → tưởng có CI mà thực tế chưa chạy bao giờ.

### Câu hỏi phỏng vấn hay gặp

- **Mock khác fake?** — mock kiểm tương tác; fake chạy thật nhưng đơn giản.
- **Test code dùng native module thế nào?** — tách logic thuần ra khỏi lớp gọi native; mock module native ở ranh giới.
- **Vì sao e2e backend dùng DB thật?** — ràng buộc DB, migration, SQL do ORM sinh ra chỉ lộ ra với DB thật.
- **Detox khác Appium?** — gray-box, tự đồng bộ với app → ít phải `sleep`.

## 2.1 Zustand trong TrailLog — hai store, và những gì nằm ngoài store

### Bức tranh tổng thể

- **Đúng 2 store:** `useAuthStore` (`src/store/authStore.ts`) và `useTrackingStore` (`src/store/trackingStore.ts`).
- **Các màn khác không dùng store** — `HistoryScreen`, `ActivitySummaryScreen`, `ConflictResolutionScreen` dùng `useState` + tự mở SQLite rồi đọc thẳng repository. Tức danh sách hoạt động **không** nằm trong state toàn cục.

### `useAuthStore` — state machine 3 trạng thái

```ts
status: 'checking' | 'signedOut' | 'signedIn';
async restoreSession() {
  const token = await tokenStorage.getToken();
  set({ status: token ? 'signedIn' : 'signedOut' });
},
```
(`authStore.ts:10`, `:20-23`) — `'checking'` đóng đúng vai trò `hasResolved` ở LexiCore: tách "chưa biết" khỏi "chưa đăng nhập". Lưu ý: `restoreSession` chỉ kiểm **có token hay không**, không kiểm hạn (xem §2.11).

### `useTrackingStore` — state công khai + state riêng tư trong closure

```ts
export const useTrackingStore = create<TrackingStoreState>((set, get) => {
  let locationService: LocationTrackingService | null = null;
  let pedometerService: PedometerService | null = null;
  let lastKnownPosition: { lat: number; lng: number } | null = null;
  let starting = false;
  return { status: 'idle', activityId: null, stepCount: 0, ... };
});
```
(`trackingStore.ts:34-45`) — đây là mẫu **closure làm state riêng tư** ở Phần 1.1: service và vị trí cuối **không** nằm trong state (UI không cần render chúng, và object service không nên bị so sánh/serialize), nhưng vẫn sống cùng vòng đời store.

**Chống double-tap bằng cờ đồng bộ** (`trackingStore.ts:47-58`):
```ts
if (starting || (locationService !== null && get().status !== 'stopped')) return;
starting = true;
try { ... } finally { starting = false; }
```
Comment giải thích: `starting` phải được đặt **trước bất kỳ `await` nào** — nếu không, hai lần bấm nhanh đều đi qua điều kiện trước khi lần đầu kịp mở SQLite, và tạo **hai** `LocationTrackingService` trên cùng một singleton native. Đây là đúng bẫy số 4 ở Phần 1.1, và có test riêng: *"ignores a second startActivity() call that fires before the first one finishes setting up"* (`trackingStore.test.ts:99`).

**Cửa sau cho test:** `__setRepositoryForTest(repo)` (`trackingStore.ts:128-130`) + biến module `testRepository` (`:24`) — cho phép test tiêm repository dùng better-sqlite3. Tiện, nhưng là **bẫy số 3 ở Phần 1.2**: API test lọt vào interface production (`TrackingStoreState` có method `__setRepositoryForTest`).

### Điểm yếu thật cần biết

1. **Không dùng selector:** `TrackingScreen` gọi `useTrackingStore()` rồi destructure (`TrackingScreen.tsx:10-20`) → màn **render lại với mọi thay đổi** — mỗi điểm GPS (`routePoints` mới) và mỗi bước chân (`stepCount`). Sửa: `useTrackingStore((s) => s.stepCount)` hoặc `useShallow`.
2. **`routePoints` giữ toàn bộ lộ trình trong RAM** và mỗi điểm tạo **mảng mới** (`[...state.routePoints, point]`, `:80`) — O(n) mỗi điểm, O(n²) cả phiên. Với phiên 3 giờ, 5 giây/điểm ≈ 2.000 điểm — chấp nhận được, nhưng là điểm cần nêu nếu bị hỏi hiệu năng.
3. **Sau `stopped` không có đường về `idle`**: `TrackingScreen` chỉ hiện nút Start khi `status === 'idle'` (`TrackingScreen.tsx:51`), còn `stopActivity` đặt `'stopped'` (`trackingStore.ts:112`). Cùng một phiên app, sau khi Stop thì màn Tracking **không còn nút nào** để bắt đầu hoạt động mới. (Tên test *"stops the activity and resets to idle"* nói "idle" nhưng assert `'stopped'` — `trackingStore.test.ts:92-97` — tên test lệch với hành vi.)

### So sánh trực tiếp

| Khía cạnh | LexiCore (Riverpod) | TrailLog (Zustand) |
|---|---|---|
| Số đơn vị state | ~16 notifier + nhiều provider hàm | 2 store |
| Auth state | `StreamNotifier` bọc `authStateChanges()` | enum `status` 3 giá trị, tự `set` |

### Cách trả lời khi bị hỏi "bạn quản lý state thế nào?" (mẫu ngắn)

## 2.3 React Navigation — auth gate bằng `initialRouteName` (và vì sao nó chưa đủ)

- **Mọi màn đều nằm trong cùng một stack** — người chưa đăng nhập về lý thuyết vẫn có thể được điều hướng tới `Home`/`History`.

Cách sửa chuẩn: điều kiện hoá cây màn — `{status === 'signedIn' ? (<>Home, Tracking, History...</>) : (<>Login, Register</>)}` — đổi trạng thái là React Navigation tự chuyển.

Comment ghi lý do: thay cho một effect chỉ chạy khi mount, vì màn History vẫn **mounted** khi bị `ConflictResolutionScreen` che lên, nên quay về thì dòng vừa giải quyết xung đột **vẫn hiện trạng thái cũ** — đúng bẫy số 2 ở Phần 1.3. Commit `9649818` sửa lỗi này.

## 2.4 SQLite offline-first — schema, migration kiểu idempotent, và những chỗ còn thô

**Ba bảng** (`src/db/schema.ts:4-34`): `activities`, `route_points`, `checkpoints`. Mọi id là **UUID v4 tạo ở client** (`activitiesRepository.ts:1-2`, `import 'react-native-get-random-values'` là polyfill bắt buộc cho `uuid` trên RN).

**Cột đồng bộ được thêm sau bằng "migration idempotent"** (`schema.ts:36-51`):
```ts
const addColumnIfMissing = async (table: string, columnDdl: string) => {
  try {
    await db.executeSql(`ALTER TABLE ${table} ADD COLUMN ${columnDdl}`);
  } catch (error) {
    if (!/duplicate column name/i.test(String(error))) throw error;
  }
};
await addColumnIfMissing('activities', 'server_id TEXT');
await addColumnIfMissing('activities', 'conflict_server_activity TEXT');
await addColumnIfMissing('checkpoints', 'server_id TEXT');
await addColumnIfMissing('checkpoints', 'photo_uploaded INTEGER NOT NULL DEFAULT 0');
```
Cách này **nâng cấp được DB cũ** (đã tạo trước khi có tính năng sync) — đúng yêu cầu migration ở Phần 1.4 — và chỉ nuốt đúng lỗi "cột đã tồn tại". Hạn chế: chỉ **thêm cột** được; đổi kiểu/đổi tên/xoá cột cần hệ thống phiên bản (`PRAGMA user_version`).

**`initSchema` chạy mỗi lần mở kết nối** (`sqliteStorageAdapter.ts:19-24`) — comment: mỗi nơi gọi (store, và các màn History/Summary **tự mở kết nối riêng**) đều phải có schema đúng; `CREATE TABLE IF NOT EXISTS` nên chạy lại là vô hại. Commit `82ddb4f` sửa lỗi màn đọc DB trước khi schema được tạo.

**Những điểm thô cần nói thẳng nếu bị hỏi (đối chiếu "Bẫy thường gặp" ở 1.4):**

| Bẫy | Trong code | Hệ quả |
|---|---|---|
| Không transaction | Port `SqlDatabase` không có API transaction; `updateActivityMetadata` chạy **2 `UPDATE` riêng** cho title và notes (`activitiesRepository.ts:130-144`) | Lỗi giữa chừng để lại nửa thay đổi. Chính việc thiếu transaction là gốc rễ của chuỗi bug sync ở §2.5 |
| N+1 query | `hydrate()` chạy 2 query con **cho mỗi hoạt động** (`:49-54`); `listActivities` gọi `hydrate` cho mọi dòng (`:125-128`) | Màn History với 100 hoạt động = 201 query, và tải **toàn bộ điểm GPS** chỉ để hiện tiêu đề |
| Nhiều kết nối | Mỗi màn gọi `createSqliteStorageAdapter()` → `SQLite.openDatabase` mới + chạy lại `initSchema` | Tốn tài nguyên; `HistoryScreen` mở thêm một kết nối mỗi lần bấm Sync (`:37`) |
| Ghi bắn-rồi-quên | `repo.addRoutePoint(activityId, point);` **không `await`, không `.catch`** (`trackingStore.ts:78`) | Lỗi ghi một điểm GPS → unhandled promise rejection, điểm mất im lặng — trong khi UI vẫn thêm điểm đó vào bản đồ |
| Không khoá ngoại/index | `route_points.activity_id`, `checkpoints.activity_id` không có `REFERENCES` hay index | Truy vấn con quét toàn bảng khi dữ liệu lớn |

**Một lỗ hổng dữ liệu thật: `ended_at` không bao giờ được ghi.** `stopActivity` chỉ dừng service và đặt `status: 'stopped'` (`trackingStore.ts:105-113`); repository **không có method nào** ghi `ended_at`. Hậu quả: mọi hoạt động có `endedAt = null` cả ở máy lẫn server — không tính được thời lượng. Và vì hoạt động ở trạng thái `pending` **ngay từ lúc tạo** (`:88-91`), không có khái niệm "đã hoàn tất, sẵn sàng đồng bộ" như design spec mô tả (*"User stops the activity. It is marked complete locally and enqueued for sync"*).

## 2.5 SyncEngine — một bug, ba lần xuất hiện, và bất biến rút ra

`src/sync/syncEngine.ts` là file **đáng kể nhất khi phỏng vấn**, vì lịch sử git của nó là một câu chuyện debug thật.

### Luồng hiện tại (`pushActivity`, `:11-99`)

```ts
if (!serverId) {
  const server = await apiClient.createActivity({ ...routePoints });
  serverId = server.id; serverUpdatedAt = server.updatedAt;
  await repo.markActivityServerId(activity.id, serverId, serverUpdatedAt); // vẫn 'pending'
} else {
  const result = await apiClient.updateActivityMetadata(serverId, { title, notes, clientUpdatedAt: activity.updatedAt });
  if ('conflict' in result) conflictPayload = JSON.stringify(result.serverActivity); // GIỮ LẠI, chưa ghi
  else serverUpdatedAt = result.updatedAt;
}
for (const checkpoint of activity.checkpoints) {
  if (!checkpoint.serverId) { /* tạo checkpoint */ await repo.markCheckpointSynced(...); }
  if (checkpoint.photoPath && !checkpoint.photoUploaded) { /* tải ảnh */ await repo.markCheckpointPhotoUploaded(...); }
}
if (conflictPayload) { await repo.markActivityConflict(activity.id, conflictPayload); return 'conflict'; }
await repo.markActivitySynced(activity.id, serverId, serverUpdatedAt);
return 'synced';
```

### Câu chuyện bug (commit `1116e94` → `e1e4c1d` → `3f0bbde`, ghi chi tiết trong `docs/superpowers/plans/2026-09-20-traillog-mobile-auth-sync.md`, ba "Design note")

1. **Lần 1:** bản đầu gọi `markActivitySynced` **trước** vòng lặp checkpoint. Vì không có transaction, checkpoint/ảnh lỗi giữa chừng → hoạt động đã `synced`, **biến khỏi hàng đợi vĩnh viễn**, checkpoint còn lại không bao giờ được đẩy, không lỗi, không cách retry. **Sửa:** thêm `markActivityServerId` (ghi `server_id` nhưng **giữ `pending`**), vòng lặp checkpoint **idempotent** (bỏ qua cái đã có `serverId`/`photoUploaded`), `markActivitySynced` chỉ chạy sau vòng lặp.
2. **Lần 2 (lỗ hổng do chính bản sửa 1 tạo ra):** (a) `markActivityServerId` ban đầu không ghi `updated_at` của server → lần resume gửi `clientUpdatedAt` = thời điểm **tạo cục bộ**, luôn cũ hơn `updatedAt` server → **mọi lần resume đều bị báo xung đột giả**; (b) nhánh xung đột `return` ngay trước vòng lặp checkpoint → lại bỏ rơi checkpoint. **Sửa:** `markActivityServerId` ghi luôn `updatedAt` của server (`activitiesRepository.ts:158-175`, comment giải thích); nhánh xung đột **vẫn chạy tiếp** vòng lặp checkpoint.
3. **Lần 3 (cùng loại bug, qua giá trị trạng thái thứ ba):** bản sửa 2 vẫn **ghi** `markActivityConflict` ngay khi phát hiện — mà `'conflict'` cũng rời hàng đợi y như `'synced'`. Checkpoint lỗi cùng lượt → mắc kẹt. **Sửa:** giữ payload trong biến `conflictPayload`, chỉ ghi sau vòng lặp (`syncEngine.ts:43-56`, `:89-92`).

**Bất biến rút ra** (câu nên nói nguyên văn khi phỏng vấn): *"Không bao giờ ghi một trạng thái làm bản ghi rời hàng đợi cho tới khi mọi bản ghi con trong cùng lượt đã thực sự lên server."* Đây là bẫy số 1 ở Phần 1.5. Mỗi lần sửa đều có test tương ứng: *"resumes a partially-synced activity on retry..."*, *"still pushes an outstanding checkpoint even when the metadata push conflicts"*, *"leaves an activity pending, not conflict, if a checkpoint fails in the same pass as a metadata conflict"* (`syncEngine.test.ts:122`, `:171`, `:199`).

### Những gì sync engine CHƯA làm (đối chiếu design spec và Phần 1.5)

| Thiếu | Hệ quả thật |

| **Idempotency phía server** | Nếu `POST /activities` thành công nhưng response mất (mạng đứt), `server_id` không được ghi → lần sau **tạo hoạt động trùng** trên server. Tương tự với checkpoint và ảnh (mỗi lần tải ảnh lưu file mới `${checkpointId}-${Date.now()}.jpg` — `activities.controller.ts:93`). Sửa: cho client gửi UUID của chính nó làm id (hoặc header `Idempotency-Key`), server `upsert` theo id đó |

## 2.6 Phát hiện xung đột — thực tế là LWW theo đồng hồ máy, không phải "cả hai cùng đổi"

**Phía server** (`backend/src/activities/activities.service.ts:43-66`):
```ts
const clientSawAt = new Date(dto.clientUpdatedAt);
if (current.updatedAt.getTime() > clientSawAt.getTime()) {
  return { status: 'conflict' as const, serverActivity: current };
}
const updated = await this.prisma.activity.update({ where: { id: activityId }, data: {...} });
```
Controller trả `{ conflict: true, serverActivity }` với **HTTP 200** (`activities.controller.ts:56-64`), không phải 409 — client phân biệt bằng hình dạng body (union type `UpdateActivityResult`, `apiClient.ts:27-29`). Có unit test cho cả trường hợp biên "bằng nhau không phải xung đột" (`activities.service.spec.ts:57`).

**Điểm tinh tế quan trọng nhất — đọc kỹ `clientUpdatedAt` là gì:**
Client gửi `clientUpdatedAt: activity.updatedAt` (`syncEngine.ts:40`). Giá trị này là:
- sau lần sync đầu: `updatedAt` **của server** (nhờ `markActivityServerId`/`markActivitySynced`) — đúng nghĩa "phiên bản tôi đã thấy";
- nhưng **sau một lần sửa cục bộ**: `new Date().toISOString()` **của điện thoại** (`activitiesRepository.ts:131`) — tức "thời điểm tôi sửa", **không còn** là phiên bản đã thấy.

Hệ quả, theo đúng Phần 1.6:

| Kịch bản | Design spec muốn | Code thật làm |
|---|---|---|
| A sửa lúc 10:00 (offline), B sửa + đồng bộ lúc 10:05, A đồng bộ lúc 10:10 | Cả hai cùng đổi → **hỏi người dùng** | `server.updatedAt (10:05) > clientUpdatedAt (10:00)` → **xung đột** ✅ |
| B sửa + đồng bộ lúc 10:00, A (offline, chưa thấy bản của B) sửa lúc 10:05, A đồng bộ | Cả hai cùng đổi → **hỏi người dùng** | `10:00 > 10:05` sai → **ghi đè im lặng** bản của B ❌ |
| Đồng hồ điện thoại A chạy nhanh 1 giờ | — | A **luôn thắng**, không bao giờ thấy xung đột |

Tức thực tế là **last-write-wins theo đồng hồ treo tường**, chỉ báo xung đột khi server được sửa *sau* thời điểm sửa cục bộ. **Cách sửa đúng:** lưu riêng một cột `server_updated_at` (base — phiên bản server lúc đồng bộ cuối) và gửi cột đó; hoặc tốt hơn là cột `version` nguyên, server `UPDATE ... WHERE id = ? AND version = ?`.

**Race phía server:** `findFirst` rồi `update` là **hai câu lệnh** (check-then-act, bẫy số 2 ở 1.6) — hai request đồng thời có thể cùng qua bước kiểm. Sửa bằng `updateMany({ where: { id, userId, updatedAt: clientSawAt } })` rồi kiểm `count`.

**Màn giải quyết xung đột** (`src/screens/ConflictResolutionScreen.tsx`):
- **"Keep mine"** (`:26-38`): gọi lại `updateActivityMetadata` với **chính tiêu đề hiện tại** → `updated_at` = bây giờ (mới hơn server) + `sync_status = 'pending'` → lượt sync sau đẩy lên qua đường chính đã được test. Comment giải thích vì sao không gọi API trực tiếp: tránh nhân đôi logic sync. Đây là bản sửa ở commit `9649818` — trước đó "Keep mine" chỉ đổi trạng thái cục bộ, **server không bao giờ nhận được**.
- **"Take server version"** (`:40-44`): chỉ lấy **`title`** của server — `notes` của server **bị bỏ qua** (bẫy số 4 ở 1.6). Và nó cũng đặt `pending`, nên lượt sau sẽ **đẩy lại** chính tiêu đề của server lên (vô hại nhưng thừa một request và làm mới `updatedAt` server).

## 2.7 Theo dõi vị trí nền — `LocationTrackingService` và cái Promise không bao giờ resolve

`src/tracking/locationTrackingService.ts` — tính năng mà design spec gọi là *"core technical bet"*, và cũng là file có **nhiều vòng sửa nhất** trong git log (`c27613f`, `6523e0f`, `919bd91`, cùng 4 commit docs sửa plan).

**State machine thuần** (`trackingStateMachine.ts:5-10`):
```ts
const ALLOWED_TRANSITIONS = {
  idle: { START: 'recording' },
  recording: { PAUSE: 'paused', STOP: 'stopped' },
  paused: { RESUME: 'recording', STOP: 'stopped' },
  stopped: {},
};
```
`transition()` **ném lỗi** khi chuyển không hợp lệ (`:19-26`) — fail loud. `stopped: {}` nghĩa là một instance service **không tái sử dụng được** — mỗi hoạt động tạo instance mới (`trackingStore.ts:77`).

**Mẹo quan trọng nhất — Promise giữ foreground service sống** (`:95-110`):
```ts
BackgroundActions.start(
  () => new Promise<void>((resolve) => { this.releaseBackgroundTask = resolve; }),
  BACKGROUND_TASK_OPTIONS,
)
```
Comment: `react-native-background-actions` coi Promise đã resolve là "task xong" và **gỡ foreground service ngay**. Nên Promise này **cố tình không bao giờ tự resolve** — hàm `resolve` được cất vào `releaseBackgroundTask` và chỉ được gọi trong `stopBackgroundKeepAlive()` (`:112-123`). Đây chính là bẫy số 1 ở Phần 1.7. Bản đầu tiên (`c27613f`) dùng vòng lặp chờ và sau đó là "generation counter" — cả hai đều có race, cuối cùng bị **thiết kế lại** thành phương án đơn giản này (`920cb95`, `919bd91`). Có test: *"keeps the background task promise pending until stop() releases it"* (`locationTrackingService.test.ts:92`).

**Pause không đụng tới service** (`:50-55`): chỉ `clearWatch`, giữ foreground service — tránh bẫy số 2 (bật/tắt service singleton mỗi lần pause gây race). Test: *"does not touch the background keep-alive task across a pause()/resume() cycle"* (`:129`).

**`stop()` là async và được `await`** (`trackingStore.ts:105-113`): comment — nếu không chờ `BackgroundActions.stop()` xong mới đặt `'stopped'`, một lần Stop-rồi-Start nhanh có thể gọi `start()` cho task mới trước khi task cũ được gỡ (commit `131f8af`). Bẫy số 3 ở Phần 1.7.

**Cấu hình GPS:** `{ enableHighAccuracy: true, distanceFilter: 5, interval: 5000 }` (`:82`) — chỉ báo khi di chuyển ≥ 5 m, chu kỳ ~5 s trên Android.

**iOS:** không có keep-alive task; dựa vào `UIBackgroundModes: location` (comment `:84-85`). **Cấu hình native nằm trong file placeholder:** `AndroidManifest.xml` có `FOREGROUND_SERVICE_LOCATION` và `foregroundServiceType="location"` (đúng yêu cầu Android 14), `Info.plist` có `UIBackgroundModes` — nhưng như cảnh báo ở đầu tài liệu, **cả hai chưa nằm trong một project build được**.

**Khoảng trống cần biết:**
- Chỉ xin quyền **foreground** (`ACCESS_FINE_LOCATION` / iOS `LOCATION_WHEN_IN_USE` — `permissionsManager.ts:23-26`), không xin `ACCESS_BACKGROUND_LOCATION`/iOS "Always". Với Android foreground service loại `location` được khởi động khi app đang mở, quyền foreground là **đủ theo tài liệu Android**; trên iOS "When In Use" + background mode vẫn nhận được vị trí nền nhưng có chỉ báo xanh. **Chưa kiểm chứng trên máy thật.**
- `onError` không được truyền từ store (`trackingStore.ts:77-81`) → lỗi GPS chỉ `console.warn`, người dùng không thấy gì.
- Nếu hệ điều hành **giết** process giữa chừng, không có cơ chế khôi phục phiên (store là in-memory; hoạt động còn trong SQLite nhưng không có gì tiếp tục ghi).

## 2.8 Đếm bước — `StepAccumulator` và bug cửa sổ trượt đã sửa

**Thuật toán** (`src/sensors/stepDetector.ts:8-10`, `:31-48`):
```ts
const GRAVITY = 9.8;
const PEAK_THRESHOLD = 2.0;        // m/s² trên trọng trường
const MIN_STEP_INTERVAL_MS = 250;  // debounce
addSample(sample) {
  const magnitude = Math.sqrt(sample.x ** 2 + sample.y ** 2 + sample.z ** 2);
  const isAboveThreshold = magnitude - GRAVITY > PEAK_THRESHOLD;
  if (isAboveThreshold && !this.wasAboveThreshold
      && sample.timestamp - this.lastPeakTimestamp >= MIN_STEP_INTERVAL_MS) { this.steps += 1; ... }
  this.wasAboveThreshold = isAboveThreshold;
}
```
Đủ ba ý ở Phần 1.8: **magnitude** (không phụ thuộc hướng máy), **cạnh lên** (`!this.wasAboveThreshold`), **debounce 250 ms**.

**Bug đã sửa (commit `11dffba` docs → `31b4d77` fix):** bản đầu chạy `detectSteps` trên **cửa sổ trượt** các mẫu gần nhất mỗi khi có mẫu mới → số bước là "số bước trong cửa sổ", bị chặn trên và có thể giảm. Bản sửa tách ra `StepAccumulator` **mang trạng thái** suốt phiên; `detectSteps` giữ lại cho xử lý batch (dùng accumulator mới mỗi lần). Comment đầu class (`:12-20`) giải thích đúng điều này — bẫy số 2 ở 1.8.

**`PedometerService`** (`pedometerService.ts`): lấy mẫu mỗi **20 ms (50 Hz)** (`:5`), `subscribe` RxJS, chặn subscribe hai lần (`:12-14`), `unsubscribe` khi stop. Chỉ gọi callback khi **có bước mới** → không cập nhật store 50 lần/giây.

**Giới hạn cần nói thẳng:**
- `setUpdateIntervalForType` được gọi **ở cấp module** (`:5`) → chạy ngay khi file được import.
- Ngưỡng 2.0 và 250 ms **chưa hiệu chỉnh trên thiết bị thật** (không thể, vì chưa có bản build). Test chỉ dùng tín hiệu sóng sin tổng hợp (`stepDetector.test.ts`).
- Dùng gia tốc kế thô thay vì pedometer phần cứng → tốn pin; và `requestMotionPermission` trên Android trả `'granted'` luôn (`permissionsManager.ts:47-50`) — đúng với gia tốc kế (không cần quyền), nhưng nếu chuyển sang `TYPE_STEP_COUNTER` thì cần `ACTIVITY_RECOGNITION`.

## 2.9 Quyền — `normalizeLocationResult` và suy giảm mềm

**Hàm chuẩn hoá thuần** (`src/permissions/permissionsManager.ts:6-20`):

**Suy giảm mềm có chủ đích** (`trackingStore.ts:64-67`, `:84-89`):

- Mọi trường hợp từ chối đều **im lặng**: bấm Start mà bị từ chối quyền thì không có gì xảy ra, không hướng dẫn mở Cài đặt khi `'restricted'`.

## 2.11 Xác thực — bcrypt + JWT, và các lỗ hổng cần nói trước khi bị hỏi

**Backend** (`backend/src/auth/auth.service.ts`):
- Đăng ký: kiểm email trùng → `ConflictException` (409) (`:14-17`); băm `bcrypt.hash(password, 10)` (`:19`); DTO bắt `@IsEmail` + `@MinLength(8)` (`register.dto.ts`).
- Đăng nhập: `if (!user || !(await bcrypt.compare(...))) throw new UnauthorizedException('Invalid email or password')` (`:27-29`) — **cùng một thông báo** cho cả hai trường hợp (tốt), nhưng khi email không tồn tại thì **bỏ qua `bcrypt.compare`** → trả lời nhanh hơn rõ rệt → **dò được email qua thời gian phản hồi** (timing-based user enumeration, 1.11). Sửa: vẫn chạy `compare` với một hash giả.
- Token: `jwtService.sign({ sub: userId, email })`, **hết hạn 7 ngày** (`auth.module.ts:13`), **không có refresh token** (design spec có).
- `JwtStrategy.validate` trả `{ userId: payload.sub, email }` → thành `req.user` (`jwt.strategy.ts:20-22`); controller đọc `req.user.userId`.

**Lỗ hổng nghiêm trọng nhất:** `secret: process.env.JWT_SECRET ?? 'replace-with-a-long-random-value'` (`auth.module.ts:12`, lặp ở `jwt.strategy.ts:16`). Nếu deploy mà quên đặt biến môi trường, server **chạy bình thường** với một secret **công khai trong repo** → ai cũng ký được token cho bất kỳ `userId` nào. Sửa: bỏ giá trị mặc định, validate env lúc khởi động (`ConfigModule.forRoot({ validationSchema })`) để server **từ chối khởi động**.

**Mobile:**
- Token lưu ở **AsyncStorage không mã hoá** (`src/api/tokenStorage.ts`) — bẫy số 3 ở 1.11; nên dùng `react-native-keychain`.
- `restoreSession` coi "có token" = đã đăng nhập, **không kiểm hạn** (`authStore.ts:20-23`).
- `apiClient` **không xử lý 401**: sau 7 ngày token hết hạn, app vẫn `'signedIn'`, mọi lần sync đều `'failed'` im lặng (vì `syncEngine` nuốt lỗi), người dùng không được đưa về màn Login.
- `API_BASE_URL = 'http://localhost:3000'` (`authStore.ts:5`) — trên **Android emulator**, `localhost` là chính emulator (phải dùng `10.0.2.2`); trên máy thật cần IP LAN/domain; và HTTP thuần (cleartext) bị Android 9+ chặn mặc định ở bản release. Tức là cấu hình hiện tại **không gọi được backend từ bất kỳ thiết bị nào** nếu không sửa.

**So sánh với LexiCore (Firebase Auth):** ở LexiCore, băm mật khẩu, refresh token, thu hồi phiên, bảo vệ brute-force đều do Firebase lo. Ở TrailLog, **mỗi thứ trong số đó là một dòng trong danh sách việc phải tự làm** — và danh sách trên cho thấy phần nào đã làm (bcrypt, thông báo lỗi chung, guard) và phần nào chưa.

## 2.12 PostgreSQL + Prisma — schema thật và kiểm tra sở hữu

**Schema** (`backend/prisma/schema.prisma`): `User`, `Activity`, `RoutePoint`, `Checkpoint`. Hai migration đã commit (`20260920094822_init`, `20260920101058_add_activities`); CI chạy `npx prisma migrate deploy` trước khi test (`.github/workflows/backend-ci.yml`).

**Thứ đáng nêu:** `findAllForUser` không `include` điểm GPS (`:25-30`) — danh sách nhẹ; `findOneForUser` thì có. Nhưng không có phân trang.

**Detox e2e** (`e2e/trackingFlow.test.ts`) — kịch bản đúng như design spec (Track → Start → giả lập vị trí → ra Home → quay lại → Stop), **nhưng**:
1. Không build được vì không có project native (cảnh báo đầu tài liệu).
2. Assert cuối `element(by.text(/\d+ route points/))` — sau khi Stop, app **ở lại `TrackingScreen`**, màn này không có dòng chữ đó (chỉ `ActivitySummaryScreen` có) → test sẽ fail kể cả khi build được.
3. Không có bước đăng nhập, trong khi app mở vào màn Login nếu chưa có token.
4. CI chạy nó trên `macos-14` (Apple Silicon) — chạy Android emulator trên runner này là điểm **cần kiểm chứng**.

**CI** (`.github/workflows/mobile-ci.yml`, `backend-ci.yml`): lint + typecheck + test cho mobile; lint + build + unit + e2e (Postgres thật) cho backend; Detox chỉ chạy khi `workflow_dispatch` (thủ công) — đúng tinh thần "e2e tốn emulator nên chạy riêng". Ban đầu cả hai workflow trigger trên nhánh `main` trong khi repo làm việc trên `master` và chưa có remote → CI chưa từng chạy (đúng bẫy số 5 ở 1.13). Đã sửa: repo được push lên GitHub (`dmTung99-dev/TrailLog`) và trigger đổi sang `master` (cùng PR). Nếu bị hỏi, nói rõ đây là lỗi cấu hình đã phát hiện và sửa, và kiểm tab Actions trước khi khẳng định CI xanh.

**Quy trình:** mọi tính năng đi qua plan trong `docs/superpowers/plans/` + TDD + review; git log cho thấy mẫu lặp lại "docs: sửa plan" → "fix: sửa code" sau mỗi vòng review — bằng chứng review đã bắt được bug thật (3 vòng SyncEngine, 3 vòng keep-alive Android, bug cửa sổ trượt của pedometer).

## Checklist ôn nhanh trước phỏng vấn

- [ ] **Zustand vs Riverpod:** nói được khác biệt "đồ thị phụ thuộc có kiểu" vs "store có subscribe"; giải thích state riêng tư trong closure của `useTrackingStore`, cờ `starting` chống double-tap, và vì sao `TrackingScreen` nên dùng selector.
- [ ] **Ports & Adapters:** vẽ được port `SqlDatabase` với 2 adapter (native + better-sqlite3), và vì sao nhờ nó mà sync engine test bằng SQL thật.
- [ ] **React Navigation:** giải thích `'checking'` ↔ `hasResolved`; vì sao `initialRouteName` là auth gate yếu và cách sửa; vì sao cần `useFocusEffect`.
- [ ] **Offline-first:** UUID phía client, `sync_status` + `server_id`, migration `addColumnIfMissing`; nêu được N+1, thiếu transaction, `addRoutePoint` không `await`, `ended_at` không được ghi.
- [ ] **SyncEngine (câu chuyện quan trọng nhất):** kể lại **ba lần** bug "rời hàng đợi quá sớm" và bất biến rút ra; giải thích `markActivityServerId` vs `markActivitySynced`; nói được vì sao vẫn có thể **tạo trùng trên server** (thiếu idempotency key) và cách sửa.
- [ ] **Xung đột:** phân biệt "phiên bản đã thấy" với "thời điểm sửa cục bộ"; chỉ ra kịch bản bị ghi đè im lặng; nêu race check-then-act phía server và cách sửa bằng `updateMany` có điều kiện; biết "Take server version" bỏ qua `notes`.
- [ ] **Chạy nền:** Android foreground service vs iOS background mode; Promise **không bao giờ tự resolve** giữ service sống; vì sao Pause không đụng tới service; vì sao `stop()` phải `await`.
- [ ] **Đếm bước:** magnitude, cạnh lên, debounce 250 ms; bug cửa sổ trượt và `StepAccumulator`.
- [ ] **Quyền:** `denied` vs `blocked`; `approximate-only`; chính sách suy giảm mềm (vị trí bắt buộc, chuyển động tuỳ chọn).
- [ ] **NestJS:** thứ tự Guard → Pipe → Handler; `whitelist` + `@Type` cho DTO lồng; vì sao `STORAGE_SERVICE` phải là `Symbol`.
- [ ] **Auth:** bcrypt vs SHA-256; JWT stateless và nhược điểm thu hồi; **nói trước** 4 lỗ hổng: secret mặc định, không refresh token, AsyncStorage không mã hoá, timing enumeration.
- [ ] **Prisma:** nested write trong một transaction; ownership check trả 404; `Activity.userId` thiếu `@relation`.
- [ ] **Testing/CI:** real-SQL fake vs mock; mock native qua `moduleNameMapper` và giới hạn của nó; e2e backend với Postgres thật + rủi ro chạy song song; vì sao Detox chưa chạy thật, và lỗi trigger CI (`main` vs `master`) đã sửa thế nào.
- [ ] **So sánh RN vs Flutter** (lý do tồn tại của dự án): Bridge/JSI vs platform channel; Hermes (JS) vs AOT Dart; `useEffect` vs `initState/dispose`; vấn đề chạy nền của OS **giống nhau** ở cả hai.
- [ ] **Trung thực về giới hạn:** nói được (không né) — chưa build trên thiết bị, sync chỉ một chiều, xung đột thực chất là LWW.
